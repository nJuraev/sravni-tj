# Техническое задание

## Агрегатор банковских продуктов Таджикистана (аналог Sravni.ru)

**Версия:** 1.0 (MVP)
**Дата:** 2026-06-04

---

## 1. Цель проекта

Веб-платформа для сравнения банковских продуктов Таджикистана (аналог sravni.ru).
Пользователь сравнивает кредиты и депозиты разных банков и может оставить заявку на
выбранный продукт. Данные о продуктах собираются автоматически парсером с сайтов банков.

---

## 2. Состав системы (монорепо)

```
sravni-tj/
├── parser/        # Go — парсер продуктов (по крону)
├── backend/       # PHP / Laravel — API + приём заявок
├── frontend/      # Vue.js — витрина сравнения + формы заявок
└── docker-compose.yml
```

| Компонент | Технология | Назначение |
|---|---|---|
| Парсер | Go | Сбор продуктов с сайтов банков по крону |
| БД | PostgreSQL | Хранилище продуктов, банков, заявок |
| Бэкенд | PHP / Laravel | REST API, приём и доставка заявок |
| Фронтенд | Vue.js | Витрина сравнения, фильтры, формы заявок |

Парсер пишет данные напрямую в общую БД PostgreSQL; Laravel читает из той же БД.

---

## 3. Парсер

- Парсит продукты с **конкретных сайтов банков** (до 20 банков:
  Эсхата, Алиф, Душанбе Сити и др.).
- **Продукты на MVP:** кредиты + депозиты.
- **Количество банков:** до 20 (точный список предоставляется заказчиком).
- **Подход к извлечению:** страница банка → Markdown (Firecrawl / Jina) →
  бесплатная AI-модель (Gemini / Qwen) извлекает структурированные данные →
  запись в PostgreSQL. AI обязан возвращать строго типизированный JSON по схеме
  (анти-галлюцинации для финансовых цифр).
- **Запуск по крону** — периодическое обновление данных.
- **Метаданные парсинга** (источник URL, время парсинга, сырой ответ AI, статус запуска)
  предварительно **не сохраняются**. Должен быть **конфиг-флаг**, включающий логирование
  этих данных (для отладки AI-извлечения при необходимости).
- **Особенности данных, которые парсер обязан учитывать:**
  - ставка зависит от срока, суммы и валюты;
  - мультивалютность: TJS, USD, EUR;
  - у банка может быть несколько доменов/сабдоменов (напр. DC: `deposit.dc.tj`, `credit.dc.tj`).

## 6. Заявки (leads) и B2B-партнёрство

- Пользователь может **оставить заявку** на продукт (кредит / депозит) прямо на сайте.
- Заявка **отправляется в банк по email** — **всегда**, независимо от партнёрского статуса
  (email банка несложно найти публично).
- **Канал доставки заявки:** предварительно — **email** на адрес банка.
- Признак «банк-партнёр» хранится у банка как опциональный атрибут (для будущей
  приоритизации/интеграции), но на доставку заявки сейчас не влияет.
- Это основа монетизации (лидогенерация).

### Форма заявки
- Поля: ФИО, телефон (и минимально необходимые данные).
- **Обязательно: согласие на обработку персональных данных** (чекбокс + ссылка на
  политику). Без согласия заявка не отправляется. Юридический момент учесть.

## 12. Дополнения по ходу реализации (актуализация)

> Разделы ниже отражают решения, принятые при разработке и уже частично внедрённые. Дополняют исходное ТЗ, не отменяя его.

### 12.1. Фактический стек (уточнение к разделу 9)
- **Бэкенд:** Laravel **13** (требует PHP **8.4** — задан в `backend/Dockerfile`).
- **AI-провайдер:** через **OpenRouter** (OpenAI-совместимый, `response_format: json_schema strict`). Ключ в корневом `.env` как `OPENROUTER_API_KEY` или `AI_API_KEY` (docker-compose принимает оба). Рекомендуемая платная модель: `deepseek/deepseek-v3.2` (~$0.5 за полный обход). Free-tier (`*:free`) нестабилен (429, обрезанный JSON, мёртвые id) — годен только для дымовых тестов.
  - **Фактический дефолт в проде** (`docker-compose.yml`, `parser/internal/extract/openrouter.go`) сейчас — `deepseek/deepseek-chat-v3.1:free`, т.е. именно free-tier, вопреки рекомендации выше. Стоит сверить осознанность выбора и при нестабильности парсинга переключить на платную модель.
  - Поддержаны также прямые провайдеры `gemini`, `qwen`, `deepseek` (без OpenRouter) — переключение через `AI_PROVIDER`.
- **Скрейпер:** `jina` работает без ключа (keyless), `firecrawl` требует ключ.

### 12.2. Подкатегории продуктов
Каждый продукт имеет `subcategory` (определяется AI при парсинге, гибрид: AI-классификация + подсказка из раздела меню сайта).
- **credit:** `consumer | mortgage | auto | business | agro | education | refinance | pawn`
- **deposit:** `term | savings | demand | kids`
- общий fallback: `other`; для `installment` — `null`.
Хранение: `products.subcategory` (VARCHAR + CHECK). На витрине — бейдж и фильтр по подкатегории.

### 12.3. Категория `installment` (рассрочка / исламское финансирование)
Помимо `credit`/`deposit` введена третья категория **`installment`** — для банков, работающих по исламской схеме (наценка вместо процента): Alif, Tawhid. У таких продуктов ставка может быть 0 (беспроцентная рассрочка).

### 12.4. Рейтинги и отзывы банков
- Пользователь может **оставить отзыв о банке** (1–5★, текст, имя, обязательный consent).
- **Премодерация:** новый отзыв `status=pending`, попадает в выдачу и в рейтинг только после `approved` (вручную через БД на MVP).
- **Рейтинг банка** = AVG/COUNT по одобренным отзывам; показывается ★ в каталоге и на странице банка.
- Таблица `bank_reviews`. Эндпоинты: `GET/POST /api/banks/{id}/reviews`.

### 12.5. Курсы валют (по банкам)
- Виджет/раздел **курсов валют**: у каждого банка свои курсы покупки/продажи (TJS/USD/EUR и др.) — **парсятся** с сайтов банков (отдельный тип источника).
- Планируемое хранение: `bank_currency_rates` (bank_id, currency, buy, sell, rate_date). (Схема/парс — в работе, не внедрено.)

### 12.6. Email доставки заявок (уточнение к разделу 6)
Адрес доставки лида хранится **на источнике** `bank_source_urls.email` (по категории: у кредита/депозита может быть свой), а **не** на банке. `banks.contact_email` — публичный справочный контакт из реестра НБТ (НЕ для доставки).

### 12.7. Поля банка из реестра НБТ
В `banks` добавлены: `slug`, `website`, `phone`, `address_ru`, `address_tg`, `contact_email`. Источник списка и контактов — реестр НБТ (`nbt.tj/ru/banking_system/banks.php`). 18 банков засеяны.

### 12.8. Решения по схеме БД (зафиксированы)
- Тарифная сетка — **отдельная таблица `product_rates`** (Вариант A) + денормализованные `products.rate_min/rate_max`.
- **1 продукт = 1 валюта** (мультивалютный продукт банка дробится парсером на N записей).
- enum-поля — **VARCHAR + CHECK** (не нативный Postgres ENUM).
- `products.status` при вставке парсером = **`active`** (сразу в выдаче, без ручного подтверждения); БД `DEFAULT` колонки остаётся `draft` — для прочих путей вставки (админка).
- `products.amount_min` — **nullable** (NULL = мин. сумма не указана; частый случай у кредитов).
- `products.term_min` — может быть `null` (тогда на витрине «до N мес.»).

### 12.9. Парсинг каталогов (index-режим)
Парсер сам определяет, является ли страница каталогом-меню (тогда обходит ссылки на детальные страницы продуктов) или прямой страницей продукта. Лимит 40 детальных страниц на источник, только домен банка.

### 12.11. Админ-панель (реализована — правит §8)
- Аутентификация: собственный token-guard (не Laravel Sanctum) — `admin_users.api_token`, пароль bcrypt. Роли: `admin` (полный доступ, включая пользователей) | `editor` (без раздела пользователей).
- Функционал: CRUD банков, CRUD продуктов + toggle статуса, просмотр/удаление лидов, CRUD админ-пользователей (только `admin`).
- **Locked fields:** у продукта есть `locked_fields` — поля (`category`, `subcategory`, `features`), вручную зафиксированные редактором в админке; повторный прогон парсера их не перезаписывает.
- **Не входит в админку** (только прямой доступ к БД): модерация отзывов (`bank_reviews.status`), курсы валют (`bank_currency_rates`).
- Frontend: `/admin/*` — CSR-only (без `/tj`-двойника, без SSR: auth-токен в `localStorage`, недоступен из Node).
- Эндпоинты: `POST /api/admin/login` (публично) → далее `auth:admin`: `GET me`, `POST logout`, `apiResource banks`, `GET banks/{id}/products`, `apiResource products except(index)` + `PATCH products/{id}/toggle`, `GET/DELETE leads`, `apiResource users except(show)`.

### 12.12. Telegram-бот: курсы валют + алерты
- Бот — часть Laravel-бэкенда (вебхук), не отдельный сервис: `TelegramWebhookController` + `TelegramService`/`RateDigestService`. Секьюрити — `VerifyTelegramWebhookSecret` (заголовок `X-Telegram-Bot-Api-Secret-Token`).
- Подписка с витрины: `POST /api/telegram/subscribe-init` → одноразовый токен (Cache, TTL 15 мин) → `deep_link` вида `t.me/<bot>?start=<token>`. `/start` в боте создаёт/обновляет запись в `users` (`telegram_id`, `api_token`) — **регистрация пользователя только через бота** (`email`/`password` теперь nullable).
- Личный кабинет `/profile` на витрине — управление подписками на алерты по курсу (`rate_alert_subscriptions`: валюта, операция buy/sell, направление above/below, порог), авторизация через `?token=` из ссылки бота.
- **Курсы валют — отдельный пайплайн парсера**, независимый от кредитов/депозитов: свой бинарник (`cmd/rates`), свой cron (`parser/railway.rates.json`: каждые 2 часа с 8:00 до 18:00 по Таджикистану), может обходиться без AI через детерминированный путь (`rate_rule` json_path на источник). После прогона — internal-webhook `/api/internal/rates-notify` (секрет) триггерит рассылку алертов подписчикам.

### 12.13. SSR + SEO/GEO-миграция
- SSR на Express (`frontend/server/index.js`) + Vite SSR entry, заголовки/meta через `@unhead/vue/server`. Админка рендерится статическим CSR-шеллом (SSR для неё бессмысленен — токен в `localStorage`).
- `/robots.txt` и `/sitemap.xml` генерятся динамически из БД (не статика), сайтмап кешируется 10 мин в памяти процесса.
- Структурированные данные (JSON-LD): `Organization`+`WebSite` на главной, `FinancialProduct`+`FAQPage` на карточке продукта.
- `hreflang` (ru/tj, реципрокно) + `x-default` на всех публичных страницах; canonical на `sravni.tj`.

### 12.14. Дизайн витрины
UX-паттерны агрегатора (референс — sravni.ru, **без копирования** их визуала/ассетов; своя палитра eskhata):

### 12.15. Ежедневные финансовые посты в Telegram-канал
- Новая интеграция, отдельная от бота §12.12 (тот отвечает пользователям в DM, этот — публикует в канал). Один cron `posts:run-scheduler` (Railway `telegram-posts`, `*/10 * * * *` — каждые 10 минут круглосуточно) совмещает генерацию и отправку в одном процессе — намеренно НЕ два отдельных cron-сервиса (по одному на генерацию/отправку), т.к. Railway-крон — это разовый контейнер на каждый тик, а не постоянный процесс с Laravel-шедулером внутри; было пересмотрено с изначального дизайна (два сервиса: `posts:generate-daily` раз в сутки + `queue:work database` раз в 10 минут) в пользу одного самодостаточного тика.
- **Генерация** (не раньше 04:00 UTC = 09:00 Душанбе, максимум раз в сутки — гейт по `finance_posts.generated_at`): тип дня детерминированно по дню недели (`PostTopicSelector::WEEKLY_PATTERN`): 4 дня — generic-тема (LRU по `post_topics.last_used_at`, гарантированный интервал повтора = размеру пула тем, ~18 дней), 2 дня — конкретный реальный продукт (`ProductSpotlightSelector`, без повтора продукта 30 дней), 1 день — снепшот текущих курсов валют (`CurrencyRateSnapshotService`, реиспользует `RateDigestService`). Если LLM в моменте недоступен — не блокирует день: следующий тик (через 10 мин) повторит попытку.
- **Анти-дубль контента**: для generic/product-дней в промпт LLM добавляется первый абзац (до 200 символов) предыдущего поста на ту же тему/продукт с инструкцией «не повторяй дословно, другой пример/угол» — иначе при повторе темы через ~18 дней LLM не знал бы, что уже писал по ней, и мог сгенерировать почти идентичный текст (статичный prompt + одна и та же тема на входе).
- Текст генерирует `LlmService` (первый LLM-клиент в Laravel; до этого AI вызывался только из Go-парсера) — провайдер/модель/ключ теми же именами env, что у парсера (`AI_PROVIDER`, `AI_API_KEY`, `AI_MODEL`), поддерживает `openrouter` и прямой `deepseek` (endpoint `api.deepseek.com`) — можно переиспользовать уже настроенный ключ парсера, не заводить отдельный OpenRouter-аккаунт.
- **Отправка откладывается на случайные 1–90 минут** без отдельной delayed-очереди: генерация сразу пишет `send_at = now() + random(1..90) мин` в `finance_posts` (`status=pending`); на каждом тике (в т.ч. в том же вызове, где произошла генерация) `SendFinancePostJob` диспатчится обычным `::dispatch()` для всех `pending`-постов с `send_at <= now()` — под общим `QUEUE_CONNECTION=sync` выполняется синхронно тут же, тем же приёмом, что и `DispatchRateAlerts`. Фактическая задержка = random(1..90) + до ~10 мин ожидания тика.
- Канал — chat_id в конфиге (`TELEGRAM_CHANNEL_ID`), без выбора канала в админке. Картинки — вне рамок MVP (TODO).
- Админка: раздел «Финансовые посты» — CRUD generic-тем (`post_topics`), превью расписания на 7 дней (`GET /api/admin/post-topics/preview`), история отправленных постов (`finance_posts`, только просмотр). Новая тема (`last_used_at = NULL`) автоматически попадает в приоритетную LRU-группу — механизм «подкинуть тему» без отдельного API.
- **kind='news' — внеплановый пост по внешнему источнику** (`POST /api/admin/finance-posts/from-source`): админ вставляет заголовок+текст новости (например, релиз Нацбанка), LLM пересказывает своими словами (не публикует исходник дословно — стиль канала + авторские права), результат сразу `status=pending` со случайным `send_at` — без предпросмотра/модерации перед отправкой (осознанное решение, не блокер). Не привязан к `WEEKLY_PATTERN` и не блокирует обычный пост дня (гейт генерации по расписанию фильтрует `kind IN (generic,product,currency)`, news не учитывается).
- **Отложено**: история курсов валют (`bank_currency_rates` хранит только последний снепшот на дату) — нужна для будущих постов о динамике за месяц/квартал; отдельная задача, не входит в текущую реализацию.
